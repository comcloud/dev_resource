# Dev Resource

面向 AI 编程时代的可复用功能能力仓库。

这个仓库用于集中保存从真实项目中提取、验证并标准化后的完整产品功能，例如聊天、登录、支付、文件上传、通知和权限系统。它希望解决一个常见问题：

> 同一个功能已经在某个项目中被反复调整并稳定运行，但换一个项目后，AI 又从零开始生成，开发者不得不再次经历相同的沟通、修复和验证过程。

`dev_resource` 不只保存代码，而是保存一个功能可以被另一个 AI 理解、选择、接入和验证所需要的完整信息。

## 核心理念

传统代码复用通常集中在函数、组件或软件包层面，但一个真实产品功能往往同时涉及：

- 用户交互与产品规则；
- 前端页面、组件和状态管理；
- API、后端业务逻辑和权限判断；
- 数据模型、数据库迁移和持久化规则；
- 并发、重试、幂等、顺序和异常恢复；
- 配置、第三方服务和运行环境；
- 自动化测试与真实验证证据。

因此，本仓库沉淀的基本单位不是一个孤立组件，而是一个完整的 **Capability（功能能力包）**。

一个能力包应该回答：

1. 这个功能解决什么问题？
2. 哪些行为属于它，哪些不属于？
3. 已验证的业务不变量是什么？
4. 哪部分代码可以直接复用？
5. 哪部分必须根据目标项目适配？
6. 接入需要哪些依赖、配置和迁移？
7. 如何证明接入后没有破坏原有逻辑？
8. 这份能力来自哪个项目和哪个版本？

## 仓库结构

所有能力统一存放在：

```text
capabilities/<feature>/<variant>/
```

- `feature`：功能的标准分类，例如 `chat`、`auth`、`payments`。
- `variant`：某个来源项目中已经验证的具体实现，通常使用来源项目名称。

示例：

```text
capabilities/
└── chat/
    ├── old-people/
    ├── customer-portal/
    └── community-app/
```

多个项目可以分别沉淀自己的聊天实现，不会互相覆盖。AI 在新项目中需要聊天功能时，可以比较这些变体的技术栈、产品边界、验证等级和适用场景，再选择最合适的实现。

## 能力包结构

每个能力变体遵循以下结构：

```text
capabilities/<feature>/<variant>/
├── capability.yaml
├── product.md
├── architecture.md
├── integration.md
├── provenance.md
├── verification.md
├── implementation/
├── contracts/
├── adapters/
└── tests/
```

### `capability.yaml`

能力包的机器可读入口。AI 应该首先读取这个文件。

它描述：

- 能力 ID、功能分类、来源变体和版本；
- 能力当前验证状态；
- 一句话摘要和检索标签；
- 适用与不适用场景；
- 来源项目和代码版本；
- 运行时、框架和数据库兼容性；
- 软件包及其他能力依赖；
- 必需和可选配置；
- 实现、契约及适配器入口；
- 验证命令。

### `product.md`

记录用户价值和产品行为，包括：

- 使用者与权限；
- 功能范围和非目标；
- 主流程、替代流程和失败流程；
- 空状态、加载状态与错误状态；
- 可以被测试的验收标准。

### `architecture.md`

记录不能仅靠阅读代码快速理解的关键逻辑，包括：

- 组件与数据流；
- 状态归属和持久化方式；
- 业务不变量；
- 授权与信任边界；
- 顺序、并发、重试、去重和幂等；
- 故障恢复和可观测性；
- 不应被随意改变的设计决策。

### `integration.md`

告诉另一个 AI 如何把能力接入新项目，包括：

- 前置条件和依赖；
- 安装与配置步骤；
- 数据库迁移和数据回填；
- 适配器选择；
- 宿主项目需要修改的位置；
- 验证、升级、回滚和移除方法。

### `provenance.md`

记录能力包的来源和提取过程，包括：

- 来源项目、远程仓库和 revision；
- 原始文件到能力包文件的映射；
- 提取过程中进行的转换；
- 主动排除的内容；
- 第三方代码的许可证和归属。

来源记录使维护者可以把能力包和经过验证的原实现进行对照，避免沉淀过程变成无法追踪的二次重写。

### `verification.md`

保存验证证据，而不是只写“功能可用”。内容包括：

- 验证日期与环境；
- 实际执行的命令；
- 测试和构建结果；
- 当前证据等级；
- 尚未覆盖的风险和缺口。

### `implementation/`

保存可复用的核心实现。核心逻辑应尽量避免依赖某个项目的页面结构、全局变量或基础设施命名。

### `contracts/`

保存稳定契约，例如：

- OpenAPI 或 HTTP API 说明；
- 数据模型与迁移 SQL；
- 事件和 WebSocket schema；
- 客户端状态约定；
- 权限及错误码契约。

### `adapters/`

保存宿主项目相关的连接方式，例如：

- Express、NestJS、Next.js 等服务端框架适配；
- SQLite、PostgreSQL 或云数据库适配；
- Web、微信小程序、iOS 或 Android 客户端适配；
- 对象存储、消息队列、鉴权和内容审核适配。

### `tests/`

保存单元测试、契约测试、集成测试、验收测试和合成 fixtures。测试重点应覆盖最容易在迁移时出现回归的业务不变量。

## 能力状态

`capability.yaml` 中的 `status` 表示能力已经获得什么级别的证据。

| 状态 | 含义 |
| --- | --- |
| `draft` | 仅完成脚手架或仍有未解决内容，不允许发布为可用能力 |
| `captured` | 功能边界、实现、来源和必要文档已经完整记录 |
| `verified` | 能力包测试和来源项目相关回归测试已经通过 |
| `portable` | 已在干净的第二个项目中完成接入，并通过验收测试 |
| `deprecated` | 为兼容性保留，但不建议用于新项目 |

状态必须基于证据提升。没有第二个项目的接入验证，就不能标记为 `portable`。

## 一句话沉淀功能

在已经实现并验证某个功能的项目中调用：

```text
使用 $deposit-feature-capability，沉淀当前项目的聊天功能。
```

更换功能名称即可：

```text
使用 $deposit-feature-capability，沉淀当前项目的文件上传功能。
```

使用者不需要重新说明仓库地址、目录结构、提取范围、验证标准和 Git 操作。`deposit-feature-capability` Skill 会自动：

1. 把中央仓库同步到本地隔离目录；
2. 从当前工作区识别来源项目；
3. 分析目标功能的完整垂直链路；
4. 自动生成 `feature` 和 `variant`；
5. 提取核心实现并拆分项目适配器；
6. 生成产品、架构、接入、来源和验证文档；
7. 保存 API、数据、事件和状态契约；
8. 运行结构校验和相关测试；
9. 创建聚焦的 Git commit；
10. 同步远程最新提交并安全推送到本仓库。

只有以下情况才应暂停并询问使用者：

- 无法从项目中识别所说的功能；
- 存在两个边界明显不同但同名的功能；
- 即将覆盖已经存在的相同来源变体；
- Git 身份验证、验证测试或安全同步失败。

## 在新项目中复用能力

当前仓库是能力的事实来源。AI 在新项目中接入功能时，应遵循以下顺序：

1. 扫描 `capabilities/*/*/capability.yaml`；
2. 根据 `feature`、`discovery.use_when`、技术栈和状态筛选候选变体；
3. 优先选择状态较高、契约清晰且与目标项目兼容的变体；
4. 阅读 `product.md`，确认产品行为和边界匹配；
5. 阅读 `integration.md` 和对应 `adapters/`；
6. 复制或转换 `implementation/`，接入 `contracts/`；
7. 应用必要的配置与数据库迁移；
8. 运行能力包测试和目标项目回归测试；
9. 记录目标项目新增的适配经验。

可以给 AI 这样的任务：

```text
请从 dev_resource 中选择最适合当前项目的聊天能力，完成接入并通过能力包和当前项目的测试。
```

在尚未达到 `portable` 状态时，AI 必须把能力包视为经过验证的参考实现，而不能假设它可以不经适配直接运行。

## 命名与版本规则

### Feature

使用稳定、通用、可检索的英文小写短横线名称：

```text
chat
auth
file-upload
push-notifications
role-permissions
```

不要把来源项目或技术栈写入 `feature`。

### Variant

默认使用来源 Git 仓库或项目目录名称，并转换为英文小写短横线格式：

```text
old-people
customer-portal
merchant-console
```

### Version

能力包使用语义化版本：

- 修复文档、测试或不改变契约的实现：patch；
- 增加兼容能力或可选行为：minor；
- 删除行为或改变稳定契约：major。

同一个来源项目再次沉淀同一功能时，应作为现有变体的版本更新处理，而不是静默覆盖，也不要创建含日期的重复目录。

## 质量要求

一个可以发布的能力包至少应满足：

- 没有未完成的 `TODO`；
- `capability.yaml` 和目录名称一致；
- 产品范围和非目标明确；
- 关键业务不变量已经记录；
- 核心实现不依赖未声明的项目全局状态；
- 所有配置只记录变量名，不包含真实值；
- 来源文件映射完整；
- 至少包含可执行的核心测试；
- 所有声明的入口文件真实存在；
- 验证命令和结果已经写入 `verification.md`；
- Git 变更只包含当前能力变体。

## 安全与隐私

禁止提交：

- `.env` 或任何真实密钥；
- Token、Cookie、证书和私钥；
- 生产数据库或用户数据；
- 真实聊天记录、手机号、身份证或其他个人信息；
- 内部服务的未脱敏访问地址；
- 构建产物、缓存和依赖目录；
- 与目标功能无关的应用代码；
- 没有许可证授权的第三方代码。

测试数据必须是人工构造或完成脱敏的合成数据。权限判断必须保留在可信服务端边界，不能只依赖客户端限制。

## Git 协作规则

中央仓库地址：

```text
git@github.com:comcloud/dev_resource.git
```

提交能力时：

- 先同步远程最新版本；
- 一次提交只处理一个能力变体；
- 只暂存 `capabilities/<feature>/<variant>/`；
- 使用类似 `feat(capability): add chat variant old-people` 的提交信息；
- 遇到冲突时停止并人工检查；
- 禁止 force push；
- 禁止为了通过验证而降低校验标准；
- 禁止修改或删除其他项目的能力变体。

## 当前示例

仓库中已经包含：

```text
capabilities/chat/old-people/
```

它是一份状态为 `verified` 的一对一聊天能力，来源于微信小程序项目，包含：

- 问候申请和同意流程；
- 互相关注授权；
- 文本、语音和图片私聊；
- 内容审核；
- SQLite 数据模型；
- HTTP 与 WebSocket 契约；
- Express/Node/SQLite 服务端适配；
- 微信小程序客户端适配；
- 幂等、消息时间和包完整性测试。

它尚未在第二个独立应用中完成完整接入，因此没有被标记为 `portable`。

## 这不是什么

本仓库不是：

- 整个项目的备份仓库；
- 只保存视觉组件的 UI 组件库；
- 没有验证证据的代码片段集合；
- 让 AI 不经分析直接复制代码的模板市场；
- npm、Maven、CocoaPods 等包管理器的替代品。

它保存的是带有产品语义、架构约束、来源信息和验证证据的软件能力资产。

## 长期方向

随着能力数量增加，可以继续建设：

- 能力搜索和兼容性匹配；
- 多个变体之间的差异比较；
- 从多个真实实现中提炼 canonical 版本；
- 自动安装和适配能力；
- 能力依赖图和版本解析；
- 跨项目可移植性测试；
- 能力质量评分和废弃策略。

最终目标不是让 AI 更快地重新写一遍功能，而是让已经被解决和验证的问题真正成为可以持续复用的软件资产。
